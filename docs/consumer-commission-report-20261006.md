# C 端分佣收益明细：实现与发布核对

## 业务口径

- 报表只读取当前登录用户 A、当前已核验且已选中的 Timo／Linky 工作区。
- 「最近 N 日」包含 UTC0 今天；「昨日」为前一个完整 UTC0 自然日。自定义日期首尾均含，最长 60 个自然日，不允许未来日期。
- 金额以已经写入 A 积分账户的正式邀请奖励账本为准。`INVITATION_REWARD`、`MCN_INCREASE` 与 `MCN_REVISION` 计入净额；`UNFREEZE` 是冻结转可用，不再计入收入。调减落在记账当天，不改写原收入日的报表。
- B 行的直接分佣来自 B 自身给 A 的一级奖励；间接分佣汇总 B 邀请的 C 给 A 的二级奖励。C 明细只显示 C 给 A 的二级积分，不展示 C 自身的钱包或总收入。
- 二级奖励的 B 归属使用收入事实发生时有效的版本化邀请关系，不按查询时的当前关系重算。历史关系无法还原时，保留 `direct_invitee_user_id=0` 的待核对金额，既不丢账也不猜测 B。
- B 列表包含当前直接下级（含零收益）和所选周期内有账本贡献的历史 B；C 下钻同样包含 B 当前直接邀请的零收益 C 和本期有历史贡献的 C。昵称来自公开资料，未设置时客户端显示本地化占位语；不返回手机号。

## 数据与压力边界

- V74 增加 `invitation_commission_report_event`（账本流水 ID 唯一，作幂等证明）和 `invitation_commission_report_daily`（A、应用、UTC 日期、B、来源用户 C、层级的积分净变动）。
- 每次正式账本入账／调增／冲减在原事务内写入事件投影和日汇总；失败则整个记账事务回滚。重复投影同一流水不会重复累计。解冻不写报表表。比原记账多两笔小写入，但用户报表请求不查询主账本或 MCN 原始事实。
- 汇总接口只按 A、应用、最多 60 日范围查日表，并用当前邀请关系表补齐零收益 B；C 下钻按 A、应用、B、周期查日表。分页每页 20 条，后端上限 50。详情再次核验 B 是否属于 A 的当前关系或所选周期历史贡献；服务端校验登录 A 和当前工作区，前端参数不能越权。
- V74 对部署前已经存在的账本做一次性回填；此阶段仍需扫描已有账本一次，不应在高峰时段对大规模数据盲目执行。部署前运维应只读统计 `invitation_reward_account_ledger` 行数、确认备份和迁移窗口；若规模超出可接受范围，应先改为分批回填方案再部署。不要把「报表查询不扫主账本」误称为「迁移从未读取主账本」。

## 上线与验收

1. 按发布 Runbook 备份并记录迁移前账本记录数、正式邀请奖励事件数及预估回填量；不改变发奖／提现开关。
2. 执行 V74 后，核对投影事件数等于既有账本中一级／二级 `INVITATION_REWARD`、`MCN_INCREASE`、`MCN_REVISION` 事件数；日表净额合计应与投影事件净额相等。核对待核对归属桶是否为零；非零则保留并排查历史关系，不人工改金额。
3. 用测试账号分别在 Timo／Linky 选择昨日、最近 3/7/14/30/60 日及 60 日自定义边界；核对 B 行、C 下钻、零收益 B、昵称缺省、分页和未核验访问拦截。核对入账、解冻、调增、调减时日报与钱包净额口径；不需要开启真实发奖来验证纯读路径。
