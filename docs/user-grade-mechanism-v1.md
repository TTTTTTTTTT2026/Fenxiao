# 用户等级机制 V1（业务决策记录）

> 状态：已确认的业务口径，待进入开发排期。本文不授权奖励、钱包、提现或付款。

## 目标

建立一套以用户直邀经营成果为依据的用户等级机制。用户达到对应等级门槛后，系统自动授予相应等级；团队负责人（团长）是该等级机制中的自动晋升结果，运营负责后续的团队管理与人工巡查。

## 唯一统计关系：直邀

等级计算只使用**直接邀请关系**，即 A 直接邀请 B 的 A→B 关系。

```text
A → B → C

A 的等级统计：只计 B
B 的等级统计：只计 C
A 不计 C，且无论未来邀请分销扩展到几层均保持如此。
```

用户等级机制与邀请裂变分成是两条不同的计算轴：

- 邀请裂变分成可以按业务需要支持一级、二级、三级及更多邀请关系层级；
- 用户等级始终只统计直属邀请用户，不跨级、不把下级的下级计入上级等级。

## 等级数据来源

每名用户在指定平台、公会范围内的等级证据由其直邀用户汇总形成。V1 已确认使用：

1. 直邀用户数量；
2. 直邀用户累计收入。

累计收入应基于 MCN 权威收入事实的最新有效版本，并按收入发生时的直邀关系归属。具体门槛、收入最终态口径和可用等级名单另行配置；本文不预设数值。

## 团长自动晋升与运营职责

```text
直邀人数 / 直邀累计收入达到等级门槛
→ 系统写入可追溯的用户等级结果
→ 系统自动授予 TEAM_LEADER（团长）等级
→ 运营管理该团长负责的运营团队、公会范围和成员边界
```

- 团长资格不得由运营绕过等级门槛直接授予；
- 运营可以按权限管理已晋升团长的团队归属与经营范围；
- 系统不自动降级或撤销已获得的等级；资格巡查、暂停或撤销由运营人工处理并留痕；
- 团队利润分成资格可作为团长等级下的附加资格，不等同于独立的用户角色。

## 实施约束

- 等级记录必须至少按 `用户 + 平台 + 公会 + 生效时间` 维度保存，不能直接复用现有全局 `distribution_role` 字段；
- 必须保存命中的规则版本、直邀人数、直邀累计收入和计算时间，支持审计；
- 后续邀请分成比例如按用户等级差异化，读取同一套等级结果；但邀请关系层级仍单独计算；

## 待定：邀请裂变分成比例口径

当前候选演算的基线是：对已绑定且 `BOUND_FINAL` 的 MCN 收入事实，直接以来源用户的原始收入金额乘邀请层级规则比例。它**不会**先乘公会经营分成比例。

后续需要由业务确认并形成独立规则矩阵：`受益用户等级 × 邀请关系层级 × 平台/国家/公会范围 → 裂变分成比例`，以及该比例是否存在总额上限。公会经营分成比例只用于团队经营利润/运营分红口径；在该待定项确认前，不得将两者相乘或混用。
- 本机制不创建奖励、余额、提现申请、付款指令或真实发放。

## 待业务补充

- 各等级名称及升级门槛；
- 是否启用 `PROMOTER` 中间等级及其门槛；
- 直邀累计收入采用 `FINAL` 事实，还是允许在每日预估中展示 `PROVISIONAL` 统计；
- 团长晋升后，运营团队是否自动创建，或仅由运营人工建立和配置。
