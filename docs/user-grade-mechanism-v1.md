# 用户等级机制 V1（业务决策记录）

> 状态：已确认的业务口径，待进入开发排期。本文不授权奖励、钱包、提现或付款。

## 目标

建立一套以用户积分为唯一评估指标、等级可由运营配置的等级机制。用户达到对应等级门槛后，系统自动授予相应等级；被标记为“授予团队负责人资格”的唯一等级，是团队负责人（团长）的自动晋升结果，运营负责后续的团队管理与人工巡查。

## 唯一统计关系：直邀

等级计算只使用**直接邀请关系**，即 A 直接邀请 B 的 A→B 关系。

```text
A → B → C

A 的等级统计：只计 B
B 的等级统计：只计 C
A 不计 C，且无论未来邀请分销扩展到几层均保持如此。
```

用户等级机制与邀请裂变分成是两条不同的计算轴：

- 邀请裂变分成可以按业务需要支持一级、二级、三级及更多邀请关系层级；
- 用户等级始终只统计直属邀请用户，不跨级、不把下级的下级计入上级等级。

## 等级数据来源：积分

每名用户的等级证据为可追溯的**积分余额/累计积分**。积分的主要来源已暂定为用户直接邀请的下级用户所创造的、已定稿的 MCN 收入事实。

- 只使用 A→B 的直接邀请，不跨级：A 只从 B 的收入获取积分；B 邀请 C 时，C 的收入只影响 B，不影响 A；
- 只读取已绑定、已归属且 `BOUND_FINAL` 的 MCN 收入事实；修订、作废和未定稿事实不直接记入积分；
- Timo、Linky 的原始平台代币不能直接相加；积分换算比例须按应用单独配置，暂不预设 1:1 换算；
- 在换算规则接通前，等级管理可以配置等级与积分门槛，但不得伪造积分或自动晋级。

具体积分事件、累计/周期口径、积分失效规则和各等级门槛另行配置；本文不预设数值。

## 团长自动晋升与运营职责

```text
积分达到等级门槛
→ 系统写入可追溯的用户等级结果
→ 如该等级授予团队负责人资格，系统自动创建团队并指定该用户为唯一负责人
→ 运营管理该团队的名称、状态、经营范围和经营信息
```

- 团长资格不得由运营绕过等级门槛直接授予；
- 每个团队只能有一名负责人；团队负责人资格只能来自指定等级，不能由运营手工授予；
- 团队成员关系可并存而非互斥：A 邀请 B 时，B 是 A 团队成员；若 B 后续达到团队负责人等级，系统另建 B 团队，B 仍保留在 A 团队的成员记录；
- 因此团队需要保存父团队关系和可并存的成员关系，不能用“转移成员”把 B 从 A 团队删除；无特殊人工处置不删除既有成员记录；
- 运营可以按权限管理已自动建立团队的名称、状态和经营范围，但不得改写团队负责人资格或邀请链；
- 系统不自动降级或撤销已获得的等级；资格巡查、暂停或撤销由运营人工处理并留痕；
- 团队利润分成资格可作为团长等级下的附加资格，不等同于独立的用户角色。

## 实施约束

- 等级记录必须至少按 `用户 + 平台 + 公会 + 生效时间` 维度保存，不能直接复用现有全局 `distribution_role` 字段；
- 必须保存命中的规则版本、积分值、积分来源版本和计算时间，支持审计；
- 后续邀请分成比例如按用户等级差异化，读取同一套等级结果；但邀请关系层级仍单独计算；

## 待定：邀请裂变分成比例口径

当前候选演算的基线是：对已绑定且 `BOUND_FINAL` 的 MCN 收入事实，直接以来源用户的原始收入金额乘邀请层级规则比例。它**不会**先乘公会经营分成比例。

后续需要由业务确认并形成独立规则矩阵：`受益用户等级 × 邀请关系层级 × 平台/国家/公会范围 → 裂变分成比例`，以及该比例是否存在总额上限。公会经营分成比例只用于团队经营利润/运营分红口径；在该待定项确认前，不得将两者相乘或混用。
- 本机制不创建奖励、余额、提现申请、付款指令或真实发放。

## 待业务补充

- 各等级名称、所需积分和展示文案（“积分”可在后续统一替换）；
- 团队经营收入的周期展示与汇率换算口径。
