# 团队树与积分等级 V1（实施基线）

> 状态：已确认，进入开发。本文不授权奖励、余额、提现或付款。

## 业务模型

用户等级以积分为唯一评估指标。等级可配置名称、编码、积分门槛与是否授予团队负责人资格；同一等级体系只能有一个等级授予团队负责人资格。

达到该等级时，系统自动：

1. 记录等级评估证据；
2. 为用户创建唯一的运营团队（若已存在则复用）；
3. 将用户设为该团队唯一负责人；
4. 根据用户的直接邀请关系，把新团队接入其上级团队树。

## 团队树示例

```text
A 达到团队负责人等级 → 创建 A 团队
A 直接邀请 B           → B 是 A 团队成员
B 达到团队负责人等级 → 创建 B 团队，B 为负责人
                         B 仍保留 A 团队成员关系
                         B 团队的父团队为 A 团队
```

团队成员关系是可并存、可追溯的关系，不采用“转移成员即删除旧归属”的模型。团队负责人是团队角色，不会覆盖成员关系。

## 数据边界

- 邀请链仍是成员归属的权威关系：只认直接邀请 A→B；
- 积分主来源暂定为直接邀请下级的 `BOUND_FINAL` MCN 收入事实。A→B→C 中，B 的收入只为 A 记分，C 的收入只为 B 记分；Timo、Linky 须各自维护“收入代币 → 积分”换算比例，未配置前不自动生成积分；
- 团队列表是运营查看和管理团队名称、状态、经营范围的入口；运营不能手工授予负责人资格，也不能改写邀请链；
- 团队经营利润仍使用已确定公式与公会经营分成比例；不再使用独立“运营分红规则”配置比例；
- 既有 `operating_team`、成员版本与运营分红规则历史保留审计兼容，不删除历史数据。

## 实施顺序

1. 扩展团队树和可并存成员关系，提供团队列表读取接口；
2. 建立用户等级管理：自定义等级、积分门槛、唯一负责人资格等级；
3. 建立积分账户与流水边界；待积分来源确认后接入积分事件；
4. 在等级达标事务内自动创建团队、建立父团队和成员关系；
5. 将后台“运营分红”入口替换为“团队列表”，保留只读历史利润与分红证据。

## 验收标准

- B 达到负责人等级后，可同时查到“B 是 A 团队成员”及“B 是 B 团队负责人”；
- 同一团队不能出现两名负责人；
- 未配置或未入账积分时，系统不产生等级晋升或团队；
- 团队列表可展示负责人、父团队、成员数、公会经营分成、经营利润与数据状态；
- 不创建任何真实奖励、余额、提现或付款记录。
